# 文档写作规范

本文约束 `docs/`、根目录文档与模块 `README.md` 的写法，保证长期可维护。

## 1. 文件名

- 描述性文档使用**中文文件名**，例如 `架构总览.md`、`部署指南.md`。
- 机器读取的入口文件保留英文名：`README.md`、`AGENTS.md`、`CLAUDE.md`、`LICENSE`。
- 代码目录内的 `README.md` 保留英文名，作为该模块的统一入口。
- 文件名不加序号前缀（ADR 除外），避免插入新文档时大面积重命名。

## 2. 目录

```text
docs/
├── 文档索引.md
├── 架构/
├── 指南/
├── 参考/
├── 运维/
├── 质量/
├── 产品/
├── 决策记录/
├── 智能协作/
├── 文档规范/
└── 常见问题.md
```

新文档放入最贴近的分册；不要为了「看起来多」而新建平行目录。

## 3. 内容结构

每篇文档建议包含：

1. 一句话说明主题与适用读者。
2. 主体：表格、步骤、示例优先于长段落。
3. 相关文档链接。

避免：

- 复制另一篇文档的大段内容（用链接代替）。
- 只写「是什么」不写「怎么验证」。
- 未经验证的命令与路径。

## 4. 语言

- 中文为主，专有名词保留英文（Vue、Vite、Pinia、Markdown、frontmatter）。
- 使用陈述句，不用「我们认为」「大概」这类模糊表述。
- 不使用 emoji 装饰标题或正文。
- 术语与 [术语表](../参考/术语表.md) 保持一致。

## 5. 链接

- 文档之间使用**相对路径**：`../架构/数据流.md`。
- 指向代码时使用反引号包裹路径，不强行做超链接。
- 链接文字写目标标题，不写「点击这里」。
- 改名文档后必须全局搜索引用并更新；提交前运行：

```bash
node scripts/check-docs.mjs
```

## 6. 命令与代码

- 命令放在 ```bash 代码块，保持可直接复制。
- 路径使用仓库相对路径，不写个人机器路径。
- 代码片段标注语言，并确保与当前实现一致。
- 涉及版本时写明确条件（如 Node `^22.18.0`）。

## 7. 表格

- 适合字段、对照、排查清单。
- 每列保持单一语义，不把长段落塞进单元格。
- 表格前后各留一个空行，保证渲染兼容。

## 8. 更新责任

| 变更 | 必须同步 |
| --- | --- |
| 目录结构 | `docs/架构/模块地图.md`、`AGENTS.md` |
| 构建命令 | `README.md`、`docs/架构/构建管线.md`、`docs/参考/脚本参考.md` |
| 内容规则 | `docs/参考/文章元数据参考.md`、`docs/指南/内容工作流.md` |
| 部署方式 | `docs/运维/部署指南.md` |
| 架构决策 | 新增 ADR，并在 `docs/文档索引.md` 登记 |
| 已知陷阱 | `docs/运维/已知行为与陷阱.md` |

## 9. 审查

文档 PR 与代码 PR 使用同一套标准：

- [ ] 链接有效。
- [ ] 命令可运行。
- [ ] 与实现一致（没有描述已删除的行为）。
- [ ] 没有泄露个人隐私或内部凭据。
- [ ] 已更新索引与相关文档。

## 10. 归档

过期但仍有历史价值的文档移入 `docs/归档/` 并在索引中标注「已过期」，
不要直接删除，避免旧链接全部失效。
