# 文档维护规范

文档的价值取决于它与实现的一致程度。以下是保持文档「新鲜」的机制。

## 1. 触发式更新

| 代码变更 | 必须更新的文档 |
| --- | --- |
| 新增 / 移动目录 | `docs/架构/模块地图.md`、`AGENTS.md` |
| 修改构建脚本或命令 | `README.md`、`docs/架构/构建管线.md`、`docs/参考/脚本参考.md` |
| 修改 Markdown 语法 | `docs/参考/扩展语法参考.md`、`docs/架构/渲染管线.md` |
| 修改 frontmatter 规则 | `docs/参考/文章元数据参考.md`、`docs/架构/数据流.md` |
| 修改数据结构 | `docs/参考/数据结构参考.md` |
| 修改部署方式 / base | `docs/运维/部署指南.md`、`docs/参考/配置参考.md` |
| 新增已知限制 | `docs/运维/已知行为与陷阱.md` |
| 新增架构决策 | 新建 ADR + `docs/文档索引.md` |
| 修改 i18n 键规范 | `docs/质量/编码规范.md`、`docs/架构/状态管理.md` |

## 2. 命名与链接

- 描述性文档用中文文件名；机器入口（`README.md` / `AGENTS.md` / `CLAUDE.md`）保留英文。
- 文档之间使用相对链接。
- 改名后必须全局搜索引用；提交前运行 `node scripts/check-docs.mjs`。

## 3. 所有权

| 范围 | 责任人 |
| --- | --- |
| 根目录入口文档 | 维护者 |
| `docs/架构/` | 进行结构改动的人 |
| `docs/指南/` | 进行流程改动的人 |
| `docs/参考/` | 对应功能的实现者 |
| `docs/运维/` | 负责部署与排障的人 |
| `docs/决策记录/` | 提出决策的人 |
| `docs/智能协作/` | 维护 Agent 工作流的人 |

没有正式分工时，遵循「谁改实现，谁改文档」。

## 4. 定期审查

建议每季度做一次文档巡检：

1. 随机抽取 5 篇文档，按其中命令实际执行一遍。
2. 对照当前目录树，确认模块地图没有过期条目。
3. 检查「已知行为与陷阱」中是否有已修复但仍保留的条目。
4. 合并重复内容，删除已失效的链接。
5. 在 `更新日志.md` 记录文档维护（可选）。

## 5. 归档而非删除

过期但仍有历史价值的文档移入 `docs/归档/`，并在 `docs/文档索引.md` 标注「已过期」。
原因：外部链接与历史 PR 可能仍在引用。

## 6. 质量红线

- 不写未验证的命令。
- 不描述已经删除的功能。
- 不复制其他文档的大段内容。
- 不在文档中暴露个人隐私、密钥、内部地址。
- 不用「显然」「众所周知」跳过关键前提。

## 7. 自动检查

`node scripts/check-docs.mjs` 负责：

- 相对链接目标存在；
- 不检查外链可达性（网络波动会误报）；
- 输出问题文件与行号。

CI 已接入该检查。扩展规则（如必须出现在索引中）可在脚本中追加。
