# 性能说明

## 1. 体积构成

| 部分 | 特点 |
| --- | --- |
| 字体 | 仓耳今楷约 18 MB，是首屏最大的单文件 |
| 图片 | 多为照片类 PNG，已生成 WebP 变体；首屏图仍占主要体积 |
| 框架 | Vue + Router + Pinia 打入 `vendor` 分包（约 90 KB 压缩后 36 KB） |
| 渲染库 | `marked`、`katex`、`mermaid`、`highlight.js` 均为动态导入 |
| 内容 | `blogs.json` 随文章数增长；详情页按需拉单篇 Markdown |

## 2. 已做的优化

1. **按需加载**：`marked` / KaTeX / Mermaid / highlight.js 只在真正渲染时加载。
2. **代码分包**：框架单独 `vendor`；Mermaid 的图类型自然拆成多个 chunk。
3. **图片 WebP**：`optimize-images.mjs` 按显示尺寸上限缩放，首屏预载图同时提供原图与 WebP。
4. **preload**：`index.html` 提前声明 7 张首屏图，与 JS 并行下载。
5. **入场加载器**：把字体、数据、图片的真实完成度纳入进度，避免「假加载」。
6. **数据缓存**：`blogStore.fetchBlogs` 只请求一次；`series` 等由内存派生。
7. **文章按需**：列表页只读 `blogs.json`，不预取全部正文（正文搜索除外）。

## 3. 体积预算（建议）

| 资源 | 建议上限 | 说明 |
| --- | --- | --- |
| 首屏 JS（gzip） | 120 KB | `index` + `vendor` |
| 单张首屏图 | 300 KB | WebP 优先 |
| 字体 | 现状 18 MB | 若替换，优先子集化 |
| 单篇文章 Markdown | 200 KB | 超大文章考虑拆分系列 |
| `blogs.json` | 150 KB | 约 300 篇以内较舒适 |

超出预算时优先处理图片与字体，而不是继续拆 JS。

## 4. 如何测量

### 构建产物体积

```bash
npm run build
```

看输出中最大的几个 chunk。`index-*.js` 与 `vendor-*.js` 是首屏关键路径；
`mermaid` 相关 chunk 只在含图表的文章加载。

### 运行时

- DevTools → Network：勾选 Disable cache，观察首屏请求数与总体积。
- Performance：关注首屏 LCP 图（Hero / 背景）与入场加载屏时长。
- Lighthouse：重点看 LCP、CLS、TBT；移动端模拟更接近真实。

### 图片对比

```bash
npm run check:images
```

## 5. 常见退化来源

| 变化 | 影响 |
| --- | --- |
| 新增全局大图并加入 preload | 首屏等待变长 |
| 把 `marked` 改回静态导入 | 首屏 JS 增加约 40 KB |
| 在列表页预取全部正文 | 请求数随文章数线性增长 |
| 给所有卡片加大阴影 / 模糊 | 低端设备滚动掉帧 |
| 在 `watch` 中做重计算 | 输入与滚动卡顿 |

## 6. 优化原则

1. 先测量，再改；不要凭感觉替换实现。
2. 优先减少**首屏关键路径**，而不是压缩非关键 chunk。
3. 不为了分数牺牲视觉：入场动画与背景是本项目的产品特征。
4. 任何影响首屏的改动，都要在发布检查清单中记录前后对比。
