# 题目要求解读

## 题目要求

词法分析把源程序切成了 Token 序列，语法分析要回答两个问题：

1. 这串 Token 能不能按照 SysY 的文法，从开始符号 `CompUnit` 一步步推导出来？
2. 如果能，把推导过程中经过的语法成分按顺序写下来。

题目说的“不涉及语义”，意思是语义阶段的那些错误码（b~h、l~n）统统不用管，语法分析只负责**结构**问题：该有的符号在不在、产生式的嵌套关系对不对。

## 输入与输出

输入是 `testfile.txt`（由评测程序提供），输出有两种互斥情况。

**情况一：没有语法错误 → 输出 `parser.txt`**

每一行是一个语法成分，只有两种形式：

| 形式 | 含义 | 举例 |
| --- | --- | --- |
| `类别码 内容` | 终结符（Token） | `INTTK int`、`SEMICN ;` |
| `<非终结符>` | 非终结符 | `<Stmt>`、`<CompUnit>` |

两条输出约定，也是本题最容易扣分的地方：

1. **终结符在匹配到的那一刻就输出**，顺序就是它在源程序中出现的顺序；
2. **非终结符在整个产生式完全匹配之后才输出**，也就是说它一定出现在自己所有子成分之后——这本质上就是语法树的**后序遍历**。

另外作业明确要求 `Decl`、`BType`、`BlockItem` 三个非终结符**不输出**：它们只是为了文法完整性而存在，没有额外信息量。

**情况二：存在语法错误 → 输出 `error.txt`**

每行 `行号 错误码`，多个错误按行号从小到大排序；并且只要存在错误，就**不输出** `parser.txt`。

语法分析阶段只会出现三个错误码（`a` 是词法阶段的非法字符，跟这里没关系）：

| 错误码 | 含义 | 出现位置 |
| --- | --- | --- |
| `i` | 缺少分号 | `ConstDecl`、`VarDecl`、各种以 `';'` 结尾的 `Stmt` |
| `j` | 缺少右小括号 | `if` / `while` / `switch`、函数定义与调用、`'(' Exp ')'`、强制类型转换 |
| `k` | 缺少右中括号 | 数组定义、数组下标、数组形参 |

这三个错误码有一个共同的坑：**报错行号取“前一个已匹配 Token”的行号**，而不是当前 Token 的行号。因为缺的符号本来就该出现在上一个 Token 后面，编译器只能把错误定位到那里。

## 这一版文法的特别之处

和理论课上讲的 SysY 相比，本实验的文法多了这些“加料”（详见《编译实验-文法解读》）：

- `switch` / `case` / `default` 语句；
- `static` 修饰的局部变量（全局不允许 `static`）；
- 强制类型转换 `'(' BType ')' UnaryExp`；
- `Number` 既可以是 `IntConst` 也可以是 `CharConst`；
- 初始化列表 `InitVal` / `ConstInitVal` 允许 `StringConst`；
- `FuncType` 有 `void` / `int` / `char` 三种。

动手写之前，务必对照文法把每一处都过一遍，评测的测试点几乎都藏在这些分支里。

# 解题思路

## 匹配 Token

我们可以将 Token 分为如下几类：

1. 非终结符——这意味着如果匹配到了非终结符，将要继续往更深层解析；
2. 必需的终结符——比如常量定义 `ConstDef` 中，必须要有赋值符号 `=`；
3. 可选或可重复的终结符——比如常量定义 `ConstDef` 中，可能会有中括号 `[]` 以定义数组；
4. 必须成对存在的终结符——也就是说，如果存在某一个终结符，就必须也有它。实验要求中仅包含错误码 `i/j/k`，涉及 `; / ) / ]` 三种。

匹配这些 Token 的思路并不相同。**如果看不懂以下我的文字思路，也不用着急，后续我会用实际例子解释**。

### 匹配非终结符

必须按照文法从顶向下继续展开，建议写成函数。函数内部再继续匹配 Token。

### 匹配必需的终结符

直接检查是否是对应的 Token，如果是，则**匹配，指针向后移**。

题目中说了不会存在不符合语法树的错误类型，因此不用管如果不是对应的 Token 的错误处理。

### 匹配可选或可重复的终结符

可以使用 `if` 体现可选分支。**检查**当前 Token，如果符合该可选的终结符，说明进入了可选分支，再在 `if` 里继续匹配。

否则，根本就不会进入 `if` 分支，继续匹配后面的其他 Token。

而重复则可以用 `while` 循环体现可重复，依旧是需要检查当前 Token。

### 匹配必须成对存在的终结符

**试图匹配**当前 Token，但如果匹配不上，则报错。

### 小结：四种动作怎么选

| 文法中的写法 | 含义 | 用什么 |
| --- | --- | --- |
| `ConstExp` | 非终结符 | 调用 `parseConstExp()` |
| `'='` | 必需终结符 | `match(...)` |
| `[ '[' ConstExp ']' ]` | 可选 | `if (check(...))` |
| `{ ',' ConstDef }` | 可重复 | `while (check(...))` |
| `';'`、`)`、`]` | 成对但可能缺 → 报 i/j/k | `expect(...)` |

## 辅助函数

仔细看我上面加粗的三段文字：“匹配，指针向后移”、“检查”、“试图匹配”，这是三个不同的想法，我们可以将其封装为三个辅助函数。

当然，这三个辅助函数都依赖于一个更加基本的辅助函数——查看一个 Token。

### 查看 Token：`peek()`

```java
private Token peek() {
    return peek(0);
}

private Token peek(int offset) {
    int index = position + offset;
    if (index < 0 || index >= tokens.size()) {
        return eofToken; // 越界统一返回 EOF 哨兵，绝不能返回 null
    }
    Token token = tokens.get(index);
    return token.getTokenType() == TokenType.EOF ? eofToken : token;
}
```

两个细节：

1. **只读不消费**，所以可以随便调用；
2. **永远不返回 `null`**。这一点非常关键：一旦某一层返回了 `null`，调用链上的 `token.getTokenType()` 会立刻抛 NPE，而 NPE 不带行号，排查起来极其痛苦。统一返回哨兵后，后续 `check(...)` 一律返回 `false`，程序就能平稳地走进错误恢复逻辑。

带偏移量的重载 `peek(1)`、`peek(2)` 用于前瞻（见后文“提取左因子”）。

### 匹配 Token：`match()`

```java
private Token match(TokenType type) {
    if (!check(type)) {
        return null;
    }
    Token token = tokens.get(position++);
    emitToken(token); // 匹配成功立刻输出，输出顺序天然正确
    return token;
}
```

`match()` 是**消费终结符的唯一正常入口**。好处是“输出”只需要写一遍：只要所有地方都不绕过它自己 `position++`，`parser.txt` 的顺序就绝不会错。

`matchOneOf()` 是它的便利版，用于 `'+' | '-'` 这种一个分支里有多个候选的情况：

```java
private Token matchOneOf(TokenType... types) {
    for (TokenType type : types) {
        if (check(type)) {
            return match(type);
        }
    }
    return null;
}
```

### 检查 Token：`check()`

```java
private boolean check(TokenType type) {
    Token token = peek();
    return token != null && token.getTokenType() == type;
}
```

没有任何副作用，专门用来“决定走哪个分支”：`if (check(TokenType.LBRACE))`、`while (check(TokenType.COMMA))`。

### 试图匹配 Token：`expect()`

```java
private Token expect(TokenType type, ErrorType errorType) {
    Token token = match(type);
    if (token != null) {
        return token;
    }

    reportSyntaxError(errorType, lineOfPreviousToken());

    // 错误恢复：返回占位 Token，保证调用方拿到非 null 值
    return new Token("", type, lineOfPreviousToken());
}
```

这是 i / j / k 三个错误码的**唯一出口**：匹配不上就报错，然后“假装匹配上了”继续往下走——这就是错误恢复。如果不恢复而是直接抛异常，那么一个缺分号就会让后面所有内容失去输出，评测里会少一大片。

`lineOfPreviousToken()` 就是前面说的行号规则：

```java
private int lineOfPreviousToken() {
    if (position > 0) {
        return tokens.get(position - 1).getLineNum();
    }
    return peek().getLineNum();
}
```

### 输出函数

```java
private void emitToken(Token token) {
    if (!outputEnabled) {
        return;
    }
    output.append(token.getTokenType()).append(' ').append(token.getTokenContent()).append('\n');
}

private void emitNonTerminal(String name) {
    if (!outputEnabled) {
        return;
    }
    output.append('<').append(name).append('>').append('\n');
}
```

`outputEnabled` 是为了后续实验复用：语法成分只在语法分析阶段需要，语义分析阶段调用 `setOutputEnabled(false)` 即可关掉。

## 写代码之前的两件事

### 消除左递归

递归子程序法要求文法**不能有左递归**，否则 `parseAddExp()` 的第一句就调用 `parseAddExp()`，直接栈溢出。SysY 的表达式部分全是左递归，但改法非常机械：

```text
AddExp → MulExp | AddExp ( '+' | '-' ) MulExp
```

改写成“先解析第一项，然后循环吃掉剩下的”：

```text
AddExp → MulExp { ( '+' | '-' ) MulExp }
```

`MulExp`、`RelExp`、`EqExp`、`LAndExp`、`LOrExp` 完全同理，五个方法长得几乎一模一样，可以说是复制粘贴改个名字。

判断哪个非终结符需要这样改：**看它产生式右部的第一个符号是不是它自己**。

### 提取左因子

`UnaryExp` 有两个分支都以 `Ident` 开头：`Ident '(' [ FuncRParams ] ')'` 和 `PrimaryExp → LVal → Ident`。它们只差“`Ident` 后面跟不跟 `(`”，所以用**一个 Token 的前瞻**就能区分：

```java
if (check(TokenType.IDENFR) && peek(1).getTokenType() == TokenType.LPARENT) {
    // 函数调用
}
```

`Stmt` 的赋值语句更麻烦：`a[i] = 1;` 要跳过下标才能看到 `=`，需要“数括号”前瞻，见后文。

## 输出的顺序是怎么来的

一定要先想清楚“什么时候输出 `<Xxx>`”。以 `int a = 1 + 2;` 中初值 `1 + 2` 的输出为例：

```text
INTCON 1
<Number>        ← parseNumber 结束
<PrimaryExp>    ← 1 构成 PrimaryExp
<UnaryExp>      ← UnaryExp → PrimaryExp
<MulExp>        ← MulExp → UnaryExp（只有一项）
<AddExp>        ← AddExp → MulExp（只有一项）
PLUS +
INTCON 2
<Number>
<PrimaryExp>
<UnaryExp>
<MulExp>        ← 右操作数解析完
<AddExp>        ← 整个二元 AddExp 解析完
<Exp>
<InitVal>
<VarDef>
```

规律是：

1. 每遇到一个运算符，说明“上一个 `AddExp` 收尾了”，于是先输出它，再解析右边；
2. 最后还要为最后一项再输出一次 `AddExp`。

所以左递归改写后的骨架永远是“**解析首项 → 输出 → 循环（吃运算符 → 解析右项 → 输出）**”：

```java
private AddExp parseAddExp() {
    int lineNum = peek().getLineNum();

    AddExp addExp = new AddExp(lineNum, parseMulExp());
    emitNonTerminal("AddExp"); // 首项收尾

    while (check(TokenType.PLUS) || check(TokenType.MINU)) {
        Token op = matchOneOf(TokenType.PLUS, TokenType.MINU);
        MulExp right = parseMulExp();

        addExp = new AddExp(lineNum, addExp, op, right);
        emitNonTerminal("AddExp"); // 每次二元合并后收尾
    }

    return addExp;
}
```

`* / %`、`< > <= >=`、`== !=`、`&&`、`||` 全部照抄这个模板。

## 分叉判断（first 集）

真正容易错的不是写产生式，而是 **“看到当前 Token，该走哪个分支”**。这时需要一组“能否作为某个产生式开头”的判断函数：

| 函数                      | 用途                                           |
| ----------------------- | -------------------------------------------- |
| `isDeclStart()`         | `BlockItem → Decl \| Stmt` 的分叉               |
| `isTopLevelDeclStart()` | `CompUnit` 中 `Decl` 与 `FuncDef` 的分叉          |
| `isFuncDefStart()`      | 判断 `int foo(` / `char foo(` / `void foo(`    |
| `isAssignmentStart()`   | `Stmt` 中赋值语句 vs 表达式语句                        |
| `canStartExp()`         | `[ Exp ] ';'` 中是否存在表达式                       |
| `isCastStart()`         | `'(' BType ')' UnaryExp` 与 `'(' Exp ')'` 的分叉 |

它们的共同特征是：**新增或修改词法单元时，这组函数必须同步过一遍**。漏改的症状非常隐蔽——不报错，但输出里少了一整片。

两个典型实现：

```java
// 顶层：int / char 后面跟 Ident 再跟 '(' 才是函数定义
private boolean isTopLevelDeclStart() {
    if (check(TokenType.CONSTTK) || check(TokenType.STATICTK)) {
        return true;
    }
    if (!check(TokenType.INTTK) && !check(TokenType.CHARTK)) {
        return false;
    }
    Token afterType = peek(1);
    if (afterType == null || afterType.getTokenType() != TokenType.IDENFR) {
        return false;
    }
    Token afterIdent = peek(2);
    return afterIdent == null || afterIdent.getTokenType() != TokenType.LPARENT;
}
```

```java
// 赋值语句：a[i + 1] = 1; 要先跳过下标才能看到 '='，所以要数括号
private boolean isAssignmentStart() {
    if (!check(TokenType.IDENFR)) {
        return false;
    }
    int index = position + 1;
    if (index < tokens.size() && tokens.get(index).getTokenType() == TokenType.LBRACK) {
        // 数 () 和 []，配平后的下一个 Token 是不是 ASSIGN
    }
    return index < tokens.size() && tokens.get(index).getTokenType() == TokenType.ASSIGN;
}
```

> 这里还有一个坑：如果下标缺少 `]`（错误 k），前瞻会失败。此时若直接返回 `false`，`parseStmt()` 会把它当表达式语句，然后在 `=` 上再报一个“缺分号”，凭空多出一个错误。所以前瞻失败时要退而求其次：只要在语句边界前能找到 `=`，就仍然按赋值语句解析，让 `parseLVal()` 去报 k。

还有一个分叉**不需要**额外判断：悬挂 `else`。递归下降里，`if` 分支解析完 then 语句后，若当前是 `else` 就继续吸收，天然实现“else 就近匹配”，不需要像理论课那样改写文法。

## 错误恢复的三个细节

1. **`expect()` 之后还要继续干活**，所以它必须返回占位 Token。占位 Token 内容为空串、行号取前一 Token 的行号；它不会多输出一行，因为 `emitToken()` 只在 `match()` 成功时调用。
2. **循环必须保证前进**。`parseBlock()`、`parseCaseStmt()` 这类“不断解析子项直到遇到结束符”的循环，一旦出错恢复时某个子项一个 Token 都没消费，`while` 就会原地打转，最终栈溢出或死循环。所以解析前后比一下位置，没前进就强制 `position++`：
   ```java
   int before = position;
   block.addItem(parseBlockItem());
   if (position == before) {
       position++;
   }
   ```
3. **同一个位置别报两次错**。`parseStmt()` 最后那个 `else` 分支就是干这个的：当前 Token 既不能开始表达式、也不是 `;`，说明前面已经报过错，此时 `skipToSyncPoint()` 静默跳到 `;` 或 `}`，不再重复报错。

`Compiler.java` 里的主流程很短，值得贴一下——它决定了“出错就不输出 `parser.txt`”这条规则：

```java
lexerAnalyzer.initLexerAnalyzer(testfileCode);
lexerAnalyzer.lexerAnalyze();

Parser parser = new Parser(TokenArrayListManager.getInstance().getTokenArrayList());
parser.parse();

if (!ErrorArrayListManager.getInstance().getErrorArrayList().isEmpty()) {
    try (PrintWriter writer = new PrintWriter(envInitializer.errorPath)) {
        ErrorArrayListManager.getInstance().getErrorArrayList().stream()
                .sorted(Comparator.comparingInt(Error::getLineNum))
                .forEach(error -> writer.println(error.getLineNum() + " " + error.getErrorType()));

    try (PrintWriter writer = new PrintWriter(envInitializer.parserPath)) {

```

注意两点：错误要**按行号排序**后输出；写文件务必用 try-with-resources（或者记得 `flush()`），否则会得到一个空文件。

## Parser 的关键字段

```java
private final List<Token> tokens;                    // 词法分析产物
private final StringBuilder output = new StringBuilder(); // parser.txt 的内容
private final Token eofToken;                        // EOF 哨兵
private int position;                                // 当前 Token 下标
private boolean outputEnabled;                       // 是否输出语法成分
```

把输出先攒在 `StringBuilder` 里而不是直接写到文件，是为了配合“有错就不输出 `parser.txt`”的规则：分析过程中根本不知道最后会不会出错。

## parseCompUnit()

```java
private CompUnit parseCompUnit() {
    int lineNum = peek().getLineNum();
    CompUnit compUnit = new CompUnit(lineNum);

    while (isTopLevelDeclStart()) {
        compUnit.addDecl(parseDecl());
    }

    while (isFuncDefStart()) {
        compUnit.addFuncDef(parseFuncDef());
    }

    compUnit.setMainFuncDef(parseMainFuncDef());

    emitNonTerminal("CompUnit");
    return compUnit;
}
```

`CompUnit → { Decl } { FuncDef } MainFuncDef` 这条产生式把“全局声明只能在函数定义之前”这个顺序约束直接表达出来了：先贪婪吃 `Decl`，再贪婪吃 `FuncDef`，最后必须有一个 `MainFuncDef`。

## parseStmt() 里的分支顺序

`Stmt` 有 14 个分支，递归下降里就是一条 `if` 链。顺序不能乱，**越具体的分支越要放前面**：

```java
if (check(TokenType.LBRACE)) { ... }                 // Block
if (check(TokenType.IFTK)) { ... }                   // if
if (check(TokenType.WHILETK)) { ... }                // while
if (check(TokenType.SWITCHTK)) { ... }               // switch
if (check(TokenType.BREAKTK)) { ... }                // break
if (check(TokenType.CONTINUETK)) { ... }             // continue
if (check(TokenType.RETURNTK)) { ... }               // return
if (check(TokenType.PRINTFTK)) { ... }               // printf
if (isAssignmentStart()) { ... }                     // LVal '=' Exp ';'
// 兜底：[ Exp ] ';'
```

`if` 分支的写法可以作为“成对括号 + 可选后续”的模板：

```java
if (check(TokenType.IFTK)) {
    Stmt stmt = new Stmt(lineNum, StmtKind.IF);
    stmt.setKeyword(match(TokenType.IFTK));
    match(TokenType.LPAREN);
    stmt.setCond(parseCond());
    expect(TokenType.RPARENT, ErrorType.MISSING_RIGHT_PARENTHESIS);

    stmt.setThenStmt(parseStmt());

    if (check(TokenType.ELSETK)) {
        match(TokenType.ELSETK);
        stmt.setElseStmt(parseStmt());
    }

    emitNonTerminal("Stmt");
    return stmt;
}
```

左括号 `(` 用的是 `match()` 而不是 `expect()`：因为错误码里没有“缺少左括号”，所以匹配不上就静默返回 `null`，不做报错。

> 但要注意 `match()` 可能返回 `null`，**不能直接解引用**。比如 `parseFuncDef()` 里如果连 `(` 都没有，后面的形参表就没法按文法解析，这时就得跳过参数直接去解析 `Block`。

## AST 要不要建？

从“通过测试点”的角度看，本阶段只要把 Token 流按顺序输出就够了，AST 完全不是必需的。

但我还是给每个非终结符建了一个节点类（都继承 `Node`，只存 `lineNum`），原因有两个：

1. **后续实验（语义分析、中间代码生成）必须要有 AST**，现在不建，以后还得把 `Parser` 重写一遍；
2. 有了 AST，想加调试打印（比如打印树的缩进结构）会非常方便，排查输出顺序问题时很好用。

顺带一提，`Node` 里的 `lineNum` 不是白存的：语义阶段报错（比如“名字重定义”）同样需要行号。

# 解析非终结符方法清单

> 说明：标记为“不输出”的三个非终结符，是因为作业要求它们在 `parser.txt` 中不出现。

## 顶层与声明

- [ ] `parseCompUnit()` — `<CompUnit>` — 输出 · `Decl` 与 `FuncDef` 都允许 0 个，但 `MainFuncDef` 必须有一个
- [ ] `parseDecl()` — 不输出 · 只做 `ConstDecl` / `VarDecl` 的转接，用 `check()` 分叉
- [ ] `parseConstDecl()` — `<ConstDecl>` — 输出 · 结尾 `';'` 用 `expect`（错误 i）
- [ ] `parseBType()` — 不输出 · 但要把 `int` / `char` 的 Token 存进 AST，语义阶段要用
- [ ] `parseConstDef()` — `<ConstDef>` — 输出 · 右中括号用 `expect`（错误 k）
- [ ] `parseConstInitVal()` — `<ConstInitVal>` — 输出 · 三分支：`ConstExp` / `'{' … '}'` / `StringConst`
- [ ] `parseVarDecl()` — `<VarDecl>` — 输出 · `['static']` 用 `if` 判断，结尾 `';'` 用 `expect`（错误 i）
- [ ] `parseVarDef()` — `<VarDef>` — 输出 · `'=' InitVal` 整体是可选的，用 `if` 包住
- [ ] `parseInitVal()` — `<InitVal>` — 输出 · 与 `ConstInitVal` 结构对称，只是内部换成 `Exp`

## 函数

- [ ] `parseFuncDef()` — `<FuncDef>` — 输出 · `'('` 缺失时无法解析形参表，要跳过参数直接解析 `Block`
- [ ] `parseMainFuncDef()` — `<MainFuncDef>` — 输出 · `'int' 'main' '(' ')' Block`，右括号用 `expect`（错误 j）
- [ ] `parseFuncType()` — `<FuncType>` — 输出 · `void` / `int` / `char` 三选一，用 `matchOneOf`
- [ ] `parseFuncFParams()` — `<FuncFParams>` — 输出 · `{ ',' FuncFParam }` 用 `while`
- [ ] `parseFuncFParam()` — `<FuncFParam>` — 输出 · 数组形参是 `'[' ']'`，中间没有表达式，右中括号用 `expect`（错误 k）

## 语句与块

- [ ] `parseBlock()` — `<Block>` — 输出 · `while` 循环里要防“不前进”死循环
- [ ] `parseBlockItem()` — 不输出 · 用 `isDeclStart()` 分叉 `Decl` / `Stmt`
- [ ] `parseStmt()` — `<Stmt>` — 输出 · 14 个分支按“先具体后宽泛”排 `if` 链，兜底是 `[ Exp ] ';'`
- [ ] `parseCaseStmt()` — `<CaseStmt>` — 输出 · 内部 `{ Stmt }` 遇到 `case` / `default` / `'}'` 都要停

## 表达式

- [ ] `parseExp()` — `<Exp>` — 输出 · 只是 `AddExp` 的包装
- [ ] `parseCond()` — `<Cond>` — 输出 · 只是 `LOrExp` 的包装
- [ ] `parseLVal()` — `<LVal>` — 输出 · 下标可选，右中括号用 `expect`（错误 k）
- [ ] `parsePrimaryExp()` — `<PrimaryExp>` — 输出 · `'(' Exp ')'` / `LVal` / `Number` 三分支
- [ ] `parseNumber()` — `<Number>` — 输出 · `IntConst` 或 `CharConst`，`matchOneOf` 返回 `null` 时构造占位常量，避免 NPE
- [ ] `parseUnaryExp()` — `<UnaryExp>` — 输出 · 函数调用 / 单目运算符 / 强转 / `PrimaryExp` 四分叉，函数调用必须先于 `PrimaryExp` 判断
- [ ] `parseUnaryOp()` — `<UnaryOp>` — 输出 · `+` / `-` / `!`
- [ ] `parseFuncRParams()` — `<FuncRParams>` — 输出 · `Exp { ',' Exp }`，别在 `)` 时误进
- [ ] `parseMulExp()` — `<MulExp>` — 输出 · 左递归改写的标准模板
- [ ] `parseAddExp()` — `<AddExp>` — 输出 · 同上
- [ ] `parseRelExp()` — `<RelExp>` — 输出 · 同上，注意 `<=` `>=` 是两个字符的 Token
- [ ] `parseEqExp()` — `<EqExp>` — 输出 · 同上
- [ ] `parseLAndExp()` — `<LAndExp>` — 输出 · 同上
- [ ] `parseLOrExp()` — `<LOrExp>` — 输出 · 同上，语法分析阶段**不要**做短路求值之类的语义加工
- [ ] `parseConstExp()` — `<ConstExp>` — 输出 · 与 `Exp` 完全同构，只是名称不同

# 自测方法

评测是黑盒的，所以自己造测试点很重要。我的习惯是：

1. **从最小程序开始**：`int main(){}`，确认 `<CompUnit> <MainFuncDef> <Block>` 的嵌套顺序对不对；
2. **每类错误单独一个文件**。这条极其重要：因为只要出错就不输出 `parser.txt`，把正确和错误混在一个文件里，等于两边都看不到；
3. **用“数量”校验深度**：比如 `1 + 2 + 3` 应该出现 3 个 `<AddExp>`、3 个 `<MulExp>`，手算一遍再和输出对数，比肉眼扫要快得多；
4. **覆盖空的情形**：空块 `{}`、空语句 `;`、`return;`、无形参函数 `int f(){}`、`{Decl}` 与 `{FuncDef}` 都为 0；
5. **覆盖嵌套**：`if` 套 `if` 且只有一个 `else`（验证就近匹配）、`switch` 里嵌 `while`、数组下标里再套函数调用；
6. **专门测 i / j / k**：每个错误码至少两个文件，一个“缺”一个“不缺”，确认不缺时不误报。

最后一定要做的：**同一批 testfile 反复回归**。语法分析改一处分支很容易碰坏另一处，有个能一键跑完并 diff 输出的小脚本能省下大量时间。

# 踩坑记录

按“被坑的先后顺序”记几条：

1. **忘输出非终结符**。`emitNonTerminal()` 写在 `return` 前面，有时提前 `return` 就漏了，表现为输出里少一行 `<Xxx>`。
2. **`match()` 返回 `null` 直接解引用**。一次词法错误就能让整个程序抛 NPE，最后只能看到 Java 堆栈而不是 `error.txt`。
3. **循环不前进**。`parseBlock()` 里遇到无法识别的 Token 时，子解析函数可能一个 Token 都不吃，`while` 就死循环。
4. **一个错误报两次**。`expect(';')` 报完 i 之后，如果不做同步，后面还会接着报一堆无关的错。
5. **`<NonTerminal>` 的位置搞反**。记住是**后序**：先输出所有子成分，最后才是自己。
6. **`StringConst` 忘了处理**。`printf` 的第一个参数、`char s[] = "abc"` 的初值都是 `STRCON`，把它当表达式解析必然报错。
7. **`switch` 里 `case` 的 `Number`**。它只接受 `IntConst` / `CharConst`，不接受一般表达式，所以要用 `parseNumber()` 而不是 `parseExp()`。
